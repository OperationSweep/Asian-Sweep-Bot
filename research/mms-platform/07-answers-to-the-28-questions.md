# Phase 7 — Direct Answers to the 28 Questions in §36

§36 of the original proposal asks reviewing agents 28 specific questions. Here are direct answers, with pointers to the detail.

| # | Question | Answer |
|---|---|---|
| 1 | Is MMS-first correct? | **Yes.** Best idea in the document. Each phase funds the next with evidence it produced. Keep the sequencing exactly as written. `01` §1.1 |
| 2 | Architectural weaknesses? | Single-hierarchy asset model; no shift calendar so every KPI is wall-clock and wrong; overlapping holds undefined; no PM; workflow engine and message broker over-built; no OT boundary; no BC/DR. `01`, `02`, `03` |
| 3 | Modular monolith, SOA or microservices? | **Modular monolith**, one Postgres, schema per module, dependency-direction lint rule in CI. Not close. `03` §3.1 |
| 4 | Which components are genuinely shared? | Identity, organisation, asset registry, documents, audit, notifications. **Not** workflow, KPI logic or reporting definitions. `03` §3.1 |
| 5 | What is over-engineered for release 1? | Workflow engine + designer, message broker, 3 of 6 notification channels, separate analytics stack, microservices, 8 of 10 AI agents, full DMS. ~18–27 weeks of removable effort. `03` §3.9 |
| 6 | Missing power-generation requirements? | PM/PPM, statutory inspections, work order types, defect register with risk-accepted deferral, outage windows, permit timestamps, plant tagging standard alignment, ISO 14224 taxonomy, hazardous-area device constraints. `02` |
| 7 | Cyber/industrial security requirements? | Purdue Level 4/5 placement with **no write path to OT ever**; historian data via IDMZ replica only; NIS Regulations 2018 / Cyber Assessment Framework scope if ≥2 GW to transmission; SSO+MFA+JML; threat model; pen test before go-live; AI data classification owned by security. `02` §2.2–2.3 |
| 8 | BC/DR architecture? | RTO 4h, RPO 15 min, read replica serving asset data during write failure, documented paper degraded mode, rehearsed restore before go-live then quarterly, retention for asset lifetime not 7 years. `02` §2.5 |
| 9 | Audit and regulatory requirements? | Statutory inspection evidence (PSSR/LOLER/electrical/insurer), append-only audit with event-time *and* record-time, ISO 55001 alignment if certification is held or sought, NIS/CAF if designated. `02` §2.2 |
| 10 | How to model the asset hierarchy? | **Functional location** (permanent position, mapped to the plant's own tagging standard) separate from **serialised equipment**, joined by dated installation records. Criticality on the location. Classes and failure modes per ISO 14224. Single most expensive thing to get wrong. `01` §1.3, `03` §3.4 |
| 11 | How to model state transitions? | Transition **table** — from/to/type/required role/required fields/side effects. Not a workflow engine. Log rejected transitions too. `03` §3.2 |
| 12 | How to stop KPI manipulation? | You cannot fully. Mitigate: working-time calendar; one primary hold with documented precedence; event-time vs record-time on every event; publish data-quality metrics beside every KPI; **no individual league tables in year one**; derive hold reasons from linked records where possible. `02` §2.6 |
| 13 | Excel migration approach? | Your §16 pipeline is sound. One correction: land legacy data in a **separate read-only store, excluded from KPI baselines**. Migrate for search and history, not for metric continuity. `05` §5.2 |
| 14 | Duplicate resolution? | Score candidates, never auto-merge, human adjudication in the exception review step, keep both records linked rather than destroying one. |
| 15 | Permission model? | RBAC as `(role × organisational scope)` grants, permissions as atoms, roles as bundles, plus explicit **field-level** rules for cost data. Log denials. Not ABAC. `03` §3.5 |
| 16 | Database architecture? | Single PostgreSQL, schema per module, append-only events table written in the same transaction as the state change, outbox table, read replica for reporting, object storage for attachments. `03` §3.1, §3.3 |
| 17 | How do Warehouse/Procurement integrate later? | Via the shared core (identity, org, assets, documents, audit, events) and the versioned event catalogue. Do **not** define their API contracts now — you will guess wrong, and a wrong committed contract is worse than none. `03` §3.3 |
| 18 | Which APIs and events to define now? | Event catalogue + versioning policy, and the read APIs. Add `PM_DUE`, `STATUTORY_DUE`, `DEFECT_DEFERRED`, `PERMIT_REQUESTED/ISSUED/RETURNED`, `OUTAGE_ASSIGNED` to your §23 list. `03` §3.3 |
| 19 | Offline / mobile in plant? | PWA, not native. Offline **read** of assets and open work orders plus **queued capture**; no offline editing of shared records in Phase 1. Run a connectivity survey in discovery. Check hazardous-area device rules and camera policy. `02` §2.4 |
| 20 | How to govern AI? | Propose-only, never write. Service principal with narrower rights than any human role, through the same permission-scoped API. Every call audit-logged. Model provider swappable including self-hosted. Keep AI out of the Phase 1 pitch. `03` §3.7 |
| 21 | What makes this better than an off-the-shelf CMMS? | Only one thing, and it is enough: **cross-departmental delay attribution that survives a management meeting**, plus the coherent multi-module roadmap on shared identity and assets. Not price — see Q22. `04` §4.3 |
| 22 | When is buying more sensible? | If SAP PM or Maximo is already licensed; multiple sites with a formal reliability function; assurance demands a widely-deployed product; **or there is no named long-term internal owner** — that last one is a veto. `04` §4.5 |
| 23 | What should the true MVP contain? | Foundation + work management with two-tap hold capture + PM + statutory + defects + permit timestamps + KPI/attribution + import/export. Full list in `05` §5.2. |
| 24 | What should be postponed? | Warehouse, procurement, contracts, invoicing, finance, DMS, workflow designer, broker, extra notification channels, native apps, full offline editing, 9 of 10 AI agents, predictive maintenance, contractor portal, multi-site rollout. `05` §5.2 |
| 25 | Acceptance tests for a production pilot? | 18 tests across functional, data integrity, non-functional and **adoption**. The adoption ones decide it: ≥90% of faults raised in-system, ≥85% of holds carrying a reason, ≥70% of events recorded within 15 minutes. `05` §5.4 |
| 26 | Performance assumptions? | 2,000 named users, 300 concurrent at shift handover, 50k functional locations, 60k work orders/yr, ~7.5m event rows at 5 years, 2 TB attachments, p95 API <400 ms. Undemanding — state it anyway. `05` §5.5 |
| 27 | What must be added now to avoid future redesign? | Functional-location/equipment split, criticality on locations, versioned event catalogue, enforced module boundaries, permission scoping, nullable cost hooks on work orders, shift calendar. `03` §3.9 |
| 28 | Is there a better overall solution? | **The strategy is right; the architecture needs the changes in `03`; and there is one option you did not consider — buy the system of record, build the intelligence layer on it, for roughly a third of the cost.** Whether that beats building depends on three questions answerable in a three-week discovery. `04` §4.4, §4.6 |
